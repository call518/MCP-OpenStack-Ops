# MCP-OpenStack-Ops Test and Validation Report

## 1. Overview

This report records live validation of the current MCP-OpenStack-Ops working
tree against a Kolla OpenStack 2025.1 test cloud.

### 1.1 Test purpose

The primary purpose is to determine whether the multi-user connection changes
proposed in issue #73 operate safely and consistently in a real OpenStack cloud
and through Claude Code. The validation specifically checks that:

1. Each regular user's requests execute with that user's Keystone permissions
   and project scope.
2. Concurrent users cannot view or modify resources belonging to another
   project.
3. Existing single-user behavior and registered MCP tools have not regressed.
4. The natural-language examples in `prompt_template.md` select and invoke
   appropriate MCP tools through the real Claude Code client.
5. Asynchronous operations are evaluated by final VM, volume, snapshot, and
   related resource states rather than API acceptance alone.
6. Missing cloud services, unsupported features, and client permission limits
   are distinguished from application defects.
7. All generated test resources are removed without leaving changes in the
   pre-existing cloud environment.

- Validation time: 2026-11-04 05:49:28 KST
- Source identity: working tree based on `a57b165`
- MCP client: installed Claude Code CLI
- MCP transports: Streamable HTTP and an isolated stdio test connection
- Scope: all registered MCP tools, all unique natural-language examples in
  `prompt_template.md`, unit tests, isolation checks, and resource cleanup

Credentials, tokens, private endpoints, project IDs, resource IDs, and private
keys are intentionally excluded.

### 5.3 Claude permission-policy limitations

Cases 19, 56, 99, 105, 107, 113, and 116 used read-like operations exposed by
tools such as `set_network_agents`, `set_compute_agents`, `set_flavor`, and
`set_metrics`. Claude Code denied those tools in `dontAsk` mode. They were not
globally allowed against the administrator MCP connection because that would
also permit potentially mutating operations on shared resources.

The corresponding deterministic `list` or `show` operations were exercised by
the direct 105-tool suite where safe.

### 5.4 Explicit substitutions and exact retests

- Case 50 created a 1 GB test volume instead of the requested 50 GB. It is not
  an exact request match. The duplicate size scenario in case 71 was retested
  with a real 50 GB volume and reached `available`.
- Case 60 requested `ubuntu-20.04`, which was absent from the test cloud. Its
  tool path used Cirros and `m1.tiny`; it is not an exact request match.
- Case 25 was retested with the available `rockylinux-9` image and `m1.small`;
  the VM reached `ACTIVE`.
- Case 40 was retested with `ubuntu-24-04` and `m1.small`; the VM reached
  `ACTIVE`.

## 6. Defects Found and Retested

### 6.1 Snapshot post-action status

`set_snapshot` created a real snapshot successfully but reported:

```text
Post-Action Status: Unknown Resource Type
```

The shared post-action lookup did not handle the `snapshot` resource type. A
snapshot lookup path and regression tests were added. A subsequent live MCP
test confirmed:

- no `Unknown Resource Type` result;
- final OpenStack snapshot state `available`;
- successful deletion of the snapshot, volume, and isolated test project.

### 6.2 Heat project ownership

Some Heat responses omit an explicit `project_id`. Treating that as the current
project could expose a foreign stack. Ownership validation now requires either
an explicit matching project ID or a matching project ID in the Heat self link.
Unknown or conflicting ownership is rejected.

Live tests confirmed that an own-project stack remained usable while a foreign
stack was excluded from lists and rejected by details and delete operations.

## 9. Conclusion

Within the tested OpenStack services, the core multi-user objective is working:

1. A regular user is scoped to the user's own project.
2. Foreign Compute, Network, Storage, and Heat resources are not exposed or
   modified.
3. Administrator and regular-user behavior remains distinct.
4. Real Claude Code MCP calls operate against the live OpenStack cloud.
5. Major VM, network, floating-IP, volume, snapshot, backup, and Heat paths
   completed successfully.
6. Asynchronous operations were verified using final resource states instead
   of treating API acceptance as completion.
7. All isolated test resources were removed after validation.

Remaining limitations are primarily caused by optional services or extensions
that are absent from the test cloud: Octavia, Aodh, Neutron QoS, floating-IP
port forwarding, a time-series metrics backend, and a centralized logging
backend.
